# MiniCore 优化路线图

本文档记录 MiniCore 后续优化的执行顺序、设计边界和验收标准，供后续按阶段实施。优先以压测数据和线上指标定位瓶颈，不以“代码看起来可能更快”作为改动依据。

## 使用方式

1. 先完成阶段 0 的基线测试和监控。
2. 每次只实施一个阶段或一个可独立回滚的子任务。
3. 实施前后对比相同场景下的吞吐、P95/P99 延迟、主线程耗时和 GC。
4. 达到验收标准后再进入下一阶段；若收益不明显，记录结论并暂停该方向。

## 当前基础

以下能力已经具备，不应在没有性能证据时重复改造：

| 能力 | 当前实现 | 后续关注点 |
| --- | --- | --- |
| 收包跨线程转发 | `NetworkMessageComponent` 使用 `ConcurrentQueue<NetworkIncomingPacket>`，网络线程只入队，Unity 主线程在 `Update` 中处理。 | 队列尚无容量上限和背压策略。 |
| 收包缓冲复用 | `EnqueueIncoming` 从 `ByteBufferPool.Shared` 租用数组，处理完成后归还。 | 池没有总容量、桶数量和超大数组限制。 |
| Handler 派发 | `AMHandler`、`ARpcHandler` 通过非泛型 invoker 契约直调，避免每包 `MethodInfo.Invoke` 和 `object[]` 参数数组。 | 启动阶段仍会反射扫描；是否生成直连注册代码由压测决定。 |
| Opcode 兼容性 | 使用稳定 manifest 和生成的 `OpcodeRegistry.Generated.cs`。 | 构建校验和协议版本治理应持续维护。 |
| 组件生命周期 | `Global` 通过 owner 记录直接引用计数，提供 `Get/GetOrAdd/Remove/ReleaseAll/Pin/Unpin/ForceRemove`。 | 增加泄漏诊断和常驻组件审计。 |

## 阶段 0：建立性能基线与观测

### 目标

让所有后续优化都有可比较的数据，先确定瓶颈在网络、序列化、业务 Handler 还是 Unity 主线程。

### 实施项

- 建立三类压测场景：Handler 微基准、Transport 基准、端到端业务场景。
- 为网络层增加可开关的统计器，避免正式环境每包产生字符串或日志。
- 每秒采集以下指标：
  - 收包/发包数量与字节数。
  - 入站队列当前长度、峰值长度和排队时长。
  - 每帧网络处理消息数、处理耗时和 `GC Alloc/Frame`。
  - RPC 成功、超时、取消和断线失败数量。
  - TCP、UDP、KCP 的 RTT、重传率、丢弃率和断开次数。
- 使用 Unity Profiler、Memory Profiler 和独立压测程序分别记录主线程、网络线程与 GC 数据。

### 验收标准

- 能稳定复现低压、中压、高压三档负载。
- 每次报告都包含平均值、P95、P99 和峰值，不只看平均 FPS。
- 可以定位一次“主线程卡顿导致网络积压”的完整链路。

## 阶段 1：入站队列背压与主线程预算

### 问题

当前 `NetworkMessageComponent.EnqueueIncoming` 会持续向 `incomingPackets` 入队，而 `ProcessQueueAsync` 会在主线程顺序处理直到队列清空。主线程卡顿、恶意流量或 Handler 变慢时，队列可能无限增长，延迟和内存占用会相互放大。

### 推荐方案

1. 为全局入站队列增加最大消息数和最大字节数。
2. 为每个 Session 增加独立的消息数、字节数或速率上限，防止单连接挤占全部预算。
3. 每帧设置处理预算，例如最大消息数或最大毫秒数；预算耗尽后留到下一帧。
4. 给协议定义优先级：断开通知、心跳、RPC 响应优先于可丢弃的普通同步消息。
5. 明确超限策略：丢弃可丢消息、暂停读取、限速或断开异常 Session；不能默认无限缓存。
6. 队列项被拒绝或丢弃时，必须立即归还 `ByteBufferPool` 数组。

### 不要做

- 不要在网络接收线程等待主线程处理完成，会把网络读取、KCP 更新和断线检测一起阻塞。
- 不要将所有消息一律丢弃；RPC 响应和断连消息需要不同策略。
- 不要仅用“每帧最多处理 N 条”而不记录积压字节数。

### 验收标准

- 主线程暂停数秒后，内存和队列长度有明确上限。
- 单个恶意 Session 不影响其他 Session 的 P95 延迟。
- 正常负载下不引入明显吞吐下降，且缓冲池没有泄漏。

## 阶段 2：RPC 生命周期与超时调度

### 问题

大量并发 RPC 的超时、断线失败、取消和回调可能造成定时任务、异常对象和锁竞争压力。

### 实施项

- 为每个 Session 和全局 RPC 表设置最大 pending 数量。
- 将 RPC 超时纳入统一调度器或时间轮，避免每个请求独立创建计时对象。
- 为请求记录截止时间、取消原因和可选的链路追踪 ID。
- 断连时批量失败 pending RPC，并统计失败原因。
- 对重复 rpcId、未知响应、过期响应输出采样日志和计数器。

### 验收标准

- 高并发超时场景下没有明显的定时器对象暴涨。
- Session 断开后 pending RPC 在确定时间内完成失败，不残留条目。
- RPC P99 延迟、超时率和队列积压可以关联分析。

## 阶段 3：缓冲池与数据所有权治理

### 问题

当前字节数组已复用，但 `ByteBufferPool` 的桶和每桶缓存数量不受限制。突发大包或异常流量可能让池长期保留大量内存。

### 实施项

- 为每个桶设置最大缓存数组数，为池设置总字节预算。
- 为超大包设置阈值：超过阈值不进入池，处理结束后交给 GC。
- 记录租用、归还、命中率、未归还数量和大包次数。
- 统一所有权规则：租用者负责在 `finally` 中归还；转交队列后由消费者负责归还。
- 审查 TCP 拼包、UDP 收包、KCP 重组和发送路径，避免额外 `byte[]`、`ToArray` 和字符串中间值。

### 验收标准

- 高峰后内存可回落到配置预算附近。
- 异常、断线、反序列化失败和丢包路径均能归还缓冲区。
- Pool 命中率、分配次数和大包行为可观测。

## 阶段 4：序列化分层与协议演进

### 问题

JSON 调试友好，但在高频状态同步中会带来字符串、对象图和 CPU 开销。

### 推荐策略

1. 保留 JSON 作为管理协议、测试协议和低频 RPC 的默认实现。
2. 只将经压测确认的高频消息迁移为 MessagePack、Protobuf、MemoryPack 或项目选定的二进制方案。
3. 保持外层包格式和 opcode 语义稳定，逐步增加协议版本或 serializer 标识，而不是一次性替换全部消息。
4. 为同一消息建立 JSON 与二进制版本的包大小、序列化耗时、反序列化耗时和 GC 对比。

### 验收标准

- 高频协议在目标设备上有明确的 CPU、GC 或带宽收益。
- 新旧协议可灰度共存，并具备回退路径。
- 业务层不需要感知 Transport 差异。

## 阶段 5：UDP/KCP 服务端韧性

### 实施项

- 限制单 IP 的建连频率、Session 数量和包速率。
- 限制单个 datagram、重组包和 KCP 缓冲区的最大尺寸。
- 对未知 conv、畸形包和过期 endpoint 快速拒绝，避免高成本解析。
- Session 超时清理改用分桶扫描或时间轮，避免连接数增大后全表扫描。
- 记录 RTT、重传、乱序、丢弃、握手失败和异常断开指标。

### 验收标准

- 异常 UDP 流量不会导致 Session 表或内存无上限增长。
- KCP 在预期丢包率下的 P99 延迟、重传率和 CPU 使用有基线数据。

## 阶段 6：生成式网络绑定（二期，可选）

### 前提

只有阶段 0 的数据证明启动扫描、字典查询、`Type` 反序列化或类型转换占比较高时才实施。本阶段不是当前性能优化的前置条件。

### 实施项

- 在 HotUpdate 生成 `GeneratedNetworkBindings.Register()`。
- 生成 Handler 实例化、opcode 注册、请求类型、响应工厂和直连委托。
- 保留当前反射扫描作为 Editor 调试或生成缺失时的明确失败路径。
- 评估 IL2CPP/AOT、热更新程序集和生成文件版本控制兼容性。

### 验收标准

- 每包处理路径不出现 `MethodInfo.Invoke`、`DynamicInvoke` 或运行时表达式编译。
- 启动耗时和派发微基准有可量化收益。
- 生成内容可重复、可审查且构建前校验失败信息明确。

## 阶段 7：Global 生命周期诊断

### 实施项

- 在 Development/Editor 模式记录 owner 获取次数、首次获取栈和持有时长。
- 场景切换或退出时输出未释放 owner 与仍 Pin 的组件清单。
- 为 `Pin` 和 `ForceRemove` 记录调用原因，禁止业务层用 `ForceRemove` 替代常规 `Remove`。
- 定期审查常驻组件：只有确实跨调用者、跨场景持续运行的服务才应 Pin。

### 验收标准

- 能定位“谁持有组件、持有几次、为何未释放”。
- 不在 Release 构建的热路径保留栈追踪或额外 GC。

## 阶段 8：UI、资源与对象池异步治理

### 实施项

- 为窗口打开、预加载、资源加载和对象池创建增加取消令牌。
- 同资源路径的并发请求做 in-flight 去重。
- 给 UI 缓存和对象池设置容量、淘汰和场景卸载策略。
- 异步完成时先检查 owner、窗口或场景是否仍有效，避免写入已销毁对象。

### 验收标准

- 窗口关闭或场景切换后不会出现延迟回调创建孤儿对象。
- 高速打开/关闭窗口时资源加载次数和对象池数量受控。

## 推荐执行顺序

| 顺序 | 阶段 | 原因 |
| --- | --- | --- |
| 1 | 阶段 0 | 没有数据就无法判断优化是否有效。 |
| 2 | 阶段 1 | 控制积压是网络稳定性的基础。 |
| 3 | 阶段 2、3 | 处理高并发时的生命周期、内存和超时压力。 |
| 4 | 阶段 4、5 | 根据实际业务决定协议升级和公网韧性投入。 |
| 5 | 阶段 6 | 仅在派发本身被证明是瓶颈时实施。 |
| 6 | 阶段 7、8 | 持续提升可维护性和异步资源正确性。 |
