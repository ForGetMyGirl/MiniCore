# MiniCore 优化路线图

本文档记录 MiniCore 后续优化的执行顺序、设计边界和验收标准，供后续按阶段实施。优先以压测数据和线上指标定位瓶颈，不以“代码看起来可能更快”作为改动依据。

## 使用方式

1. 先完成阶段 0 的基线测试和监控。
2. 每次只实施一个阶段或一个可独立回滚的子任务。
3. 实施前后对比相同场景下的吞吐、P95/P99 延迟、主线程耗时和 GC。
4. 达到验收标准后再进入下一阶段；若收益不明显，记录结论并暂停该方向。

## 已确认优化记录

### 2026-07-15：关闭日志时的网络热路径跳过字符串构造

| 项目 | 记录 |
| --- | --- |
| 优化范围 | `LogSwitch` 默认开关策略，以及 `NetworkService` 的收包、普通发送、RPC 请求和 RPC 响应日志路径；仅调整日志关闭时的热路径，不改变网络包处理语义。 |
| 原始问题 | 旧路径在 `LogSwitch.EnableLog = false` 时仍会先格式化时间、构造插值日志字符串，再进入已关闭的 `LogSwitch.Info`。日志输出被抑制，但每包字符串与时间格式化成本已经发生。 |
| 基线与归因证据 | `NetworkIncomingLogPerformanceTests.cs` 使用相同日志文本对比旧写法与候选写法，均在日志关闭状态下每组执行 `10,000` 次。旧路径 `IncomingLog_BuildsStrings_WhenLoggingDisabled` 三次中位值为 `22.116 / 22.168 / 22.318 ms`，每次 `GC() = 10.0005`；优化路径 `IncomingLog_SkipsStrings_WhenLoggingDisabled` 三次中位值为 `0.034 / 0.036 / 0.036 ms`，每次 `GC() = 0`。 |
| 实施方案 | `LogSwitch` 在 Editor/Development 默认开启、正式非开发构建默认关闭；`NetworkService` 的收包、普通发送、RPC 请求和 RPC 响应日志均先判断 `EnableLog`，再格式化时间和字符串；Payload 日志同时要求 `EnableLog && EnablePayloadLog`。 |
| 前后性能数据 | 关闭日志时的收包日志热路径从旧路径中位数约 `22.168 ms / 10,000 次` 降至优化路径约 `0.036 ms / 10,000 次`，约减少 `99.84%`；`GC.Alloc` 采样从稳定 `10.0005` 归零。 |
| 测试状态 | 框架阶段性能验证已确认；尚未做真实业务网络冒烟验证。 |
| 残余风险 | 日志开启时仍会保留诊断字符串构造成本；正式包默认关闭日志可避免热路径分配，但需要确认外部调试流程不会依赖正式非开发构建默认输出网络日志。 |
| 下一步 | 在真实 TCP/UDP/KCP 收发场景做一次业务网络冒烟验证，并继续观察 Payload 日志只在显式开启时转换正文。 |

### 2026-07-15：收包缓冲池稳定 GC 消除

| 项目 | 记录 |
| --- | --- |
| 优化范围 | `Network/Transport/Entity/Common/ByteBufferPool.cs`，不改变 TCP、UDP、KCP 和网络组件对 `Rent/Return` 的调用方式。 |
| 原始问题 | 旧实现使用 `ConcurrentStack<byte[]>` 保存空闲数组。数组本身被复用，但每次 `Push` 会产生短命的并发容器内部节点。 |
| 归因证据 | 10,000 次、512 B 的 `Buffer.BlockCopy` 为 `0.156 ms / GC() = 5`；`ConcurrentQueue` 入出队为 `0.464 ms / GC() = 5`；旧缓冲池仅 `Rent/Return` 为 `1.506 ms / GC() = 10005`。因此稳定分配来自缓冲池容器，而非复制或收包队列。 |
| 实施方案 | 每个大小桶替换为内部加锁的 `byte[][]` 槽位栈；稳定阶段只读写已有数组引用，不创建并发栈节点。外部调用方不需要加锁。 |
| 容量边界 | 最大池化单数组 1 MB，单桶最多保留 8 MB，所有桶合计最多保留 32 MB；桶满或超大数组归还时不缓存，避免峰值内存长期滞留。 |
| 性能结果 | 新缓冲池仅 `Rent/Return` 三次为 `1.391 / 1.398 / 1.399 ms`，中位数约 `1.398 ms`，较旧基线约快 `7%`；`GC()` 从 `10005` 降至 `5`。 |
| 端到端结果 | 完整收包交接旧基线中位数约 `3.201 ms / GC() = 10005`；新实现三次为 `2.983 / 3.007 / 3.039 ms`，中位数约 `3.007 ms / GC() = 5`，耗时约降低 `6%`。 |
| 验证状态 | 性能测试已确认，静态 C# 编译与差异格式检查通过；`ByteBufferPoolTests` 已新增，仍应在 Unity EditMode Test Runner 中手动运行一次。 |
| 残余风险 | 首次预热、桶扩容或工作负载超过容量上限时仍会创建 `byte[]`，这是池容量不足的可观测信号；后续应增加运行时命中率、桶满丢弃和保留字节数统计。 |

## 当前基础

以下能力已经具备，不应在没有性能证据时重复改造：

| 能力 | 当前实现 | 后续关注点 |
| --- | --- | --- |
| 收包跨线程转发 | `NetworkService` 使用 `ConcurrentQueue<NetworkIncomingPacket>`，网络线程只入队，Unity 主线程在 `Update` 中处理。 | 队列尚无容量上限和背压策略。 |
| 收包缓冲复用 | `EnqueueIncoming` 从 `ByteBufferPool.Shared` 租用数组，处理完成后归还；每桶使用内部加锁的数组槽位栈。 | 单数组 1 MB、单桶 8 MB、全局 32 MB 上限已落实；后续补运行时命中率和容量统计。 |
| Handler 派发 | `AMHandler`、`ARpcHandler` 通过非泛型 invoker 契约直调，避免每包 `MethodInfo.Invoke` 和 `object[]` 参数数组。 | 启动阶段仍会反射扫描；是否生成直连注册代码由压测决定。 |
| Opcode 兼容性 | 使用稳定 manifest 和生成的 `OpcodeRegistry.Generated.cs`。 | 构建校验和协议版本治理应持续维护。 |
| 组件生命周期 | `Global` 通过 owner 记录直接引用计数，提供 `Get/GetOrAdd/Remove/ReleaseAll/Pin/Unpin/ForceRemove`。 | 增加泄漏诊断和常驻组件审计。 |

## 阶段 0：建立性能基线与观测

### 目标

让所有后续优化都有可比较的数据，先确定瓶颈在网络、序列化、业务 Handler 还是 Unity 主线程。

### 实施项

- 建立三类压测场景：Handler 微基准、Transport 基准、端到端业务场景。
- 为网络层增加可开关的统计器，避免正式环境每包产生字符串或日志。
- 每秒采集以下指标：
  - 收包/发包数量与字节数。
  - 入站队列当前长度、峰值长度和排队时长。
  - 每帧网络处理消息数、处理耗时和 `GC Alloc/Frame`。
  - RPC 成功、超时、取消和断线失败数量。
  - TCP、UDP、KCP 的 RTT、重传率、丢弃率和断开次数。
- 使用 Unity Profiler、Memory Profiler 和独立压测程序分别记录主线程、网络线程与 GC 数据。

### 验收标准

- 能稳定复现低压、中压、高压三档负载。
- 每次报告都包含平均值、P95、P99 和峰值，不只看平均 FPS。
- 可以定位一次“主线程卡顿导致网络积压”的完整链路。

## 阶段 1：入站队列背压与主线程预算

### 问题

当前 `NetworkService.EnqueueIncoming` 会持续向 `incomingPackets` 入队，而 `ProcessQueueAsync` 会在主线程顺序处理直到队列清空。主线程卡顿、恶意流量或 Handler 变慢时，队列可能无限增长，延迟和内存占用会相互放大。

### 推荐方案

1. 为全局入站队列增加最大消息数和最大字节数。
2. 为每个 Session 增加独立的消息数、字节数或速率上限，防止单连接挤占全部预算。
3. 每帧设置处理预算，例如最大消息数或最大毫秒数；预算耗尽后留到下一帧。
4. 给协议定义优先级：断开通知、心跳、RPC 响应优先于可丢弃的普通同步消息。
5. 明确超限策略：丢弃可丢消息、暂停读取、限速或断开异常 Session；不能默认无限缓存。
6. 队列项被拒绝或丢弃时，必须立即归还 `ByteBufferPool` 数组。

### 不要做

- 不要在网络接收线程等待主线程处理完成，会把网络读取、KCP 更新和断线检测一起阻塞。
- 不要将所有消息一律丢弃；RPC 响应和断连消息需要不同策略。
- 不要仅用“每帧最多处理 N 条”而不记录积压字节数。

### 验收标准

- 主线程暂停数秒后，内存和队列长度有明确上限。
- 单个恶意 Session 不影响其他 Session 的 P95 延迟。
- 正常负载下不引入明显吞吐下降，且缓冲池没有泄漏。

## 阶段 2：RPC 生命周期与超时调度

### 问题

大量并发 RPC 的超时、断线失败、取消和回调可能造成定时任务、异常对象和锁竞争压力。

### 实施项

- 为每个 Session 和全局 RPC 表设置最大 pending 数量。
- 将 RPC 超时纳入统一调度器或时间轮，避免每个请求独立创建计时对象。
- 为请求记录截止时间、取消原因和可选的链路追踪 ID。
- 断连时批量失败 pending RPC，并统计失败原因。
- 对重复 rpcId、未知响应、过期响应输出采样日志和计数器。

### 验收标准

- 高并发超时场景下没有明显的定时器对象暴涨。
- Session 断开后 pending RPC 在确定时间内完成失败，不残留条目。
- RPC P99 延迟、超时率和队列积压可以关联分析。

## 阶段 3：缓冲池与数据所有权治理

### 问题

2026-07-15 的微基准确认旧版 `ConcurrentStack<byte[]>` 会在每次归还数组时产生内部节点分配：`10,000` 次 `Rent/Return` 的 `GC()` 为 `10005`。当前已替换为每桶内部加锁的 `byte[][]` 槽位栈，并设置单数组 1 MB、单桶 8 MB、全局 32 MB 的保留上限；峰值时的首次扩容和容量超限仍需要通过指标观察。

### 实施项

- 保持每桶缓存数组数和池总字节预算的边界测试，防止后续修改突破当前上限。
- 记录租用、归还、命中率、未归还数量、桶满丢弃和大包次数。
- 统一所有权规则：租用者负责在 `finally` 中归还；转交队列后由消费者负责归还。
- 审查 TCP 拼包、UDP 收包、KCP 重组和发送路径，避免额外 `byte[]`、`ToArray` 和字符串中间值。

### 验收标准

- 高峰后内存可回落到 32 MB 总保留预算附近。
- 异常、断线、反序列化失败和丢包路径均能归还缓冲区。
- Pool 命中率、分配次数和大包行为可观测。

## 阶段 4：Protobuf 协议演进与 JSON 对比基线

### 问题

当前正式网络路径使用 Protobuf。JSON 仍适合迁移验证、调试或低频兼容场景，但会带来字符串、对象图和 CPU 开销；不能再被视为网络默认实现。

### 推荐策略

1. 以 `ProtobufSerializer`、Proto 角色生成和 Parser Registry 作为正式协议链路。
2. 保留 `NewtonsoftJsonSerializer` 与 JSON 性能测试作为迁移对比，不将其重新设为默认 serializer。
3. 保持 12 字节外层包格式、Opcode 语义和 `RpcId` 头字段稳定；业务字段只在 Proto Body 中演进。
4. 为同一消息持续记录 JSON 与 Protobuf 的包大小、序列化耗时、反序列化耗时、完整入站包和 RPC 的 GC 对比。

### 验收标准

- Protobuf 正式路径在目标设备上有可重复的 CPU、GC 与带宽基线。
- JSON 对比实现不会影响 Player 默认网络路径，也不会破坏现有 Proto/Opcode 兼容性。
- 业务层不需要感知 Transport 差异。

## 阶段 5：UDP/KCP 服务端韧性

### 实施项

- 限制单 IP 的建连频率、Session 数量和包速率。
- 限制单个 datagram、重组包和 KCP 缓冲区的最大尺寸。
- 对未知 conv、畸形包和过期 endpoint 快速拒绝，避免高成本解析。
- Session 超时清理改用分桶扫描或时间轮，避免连接数增大后全表扫描。
- 记录 RTT、重传、乱序、丢弃、握手失败和异常断开指标。

### 验收标准

- 异常 UDP 流量不会导致 Session 表或内存无上限增长。
- KCP 在预期丢包率下的 P99 延迟、重传率和 CPU 使用有基线数据。

## 阶段 6：生成式 Handler 绑定（已完成，持续监控）

当前实现已在 Editor 编译后扫描 `MiniCore.HotUpdate` 的 `AMHandler<T>` 与 `ARpcHandler<TRequest,TResponse>`，生成 `HotUpdateHandlerRegistry.Generated.cs` 与 `OpcodeRegistry.Generated.cs`。运行时直接构造并注册 Handler，不扫描 AppDomain，不以字符串或 `Activator` 创建 Handler。

### 持续项

- 保持删除/改名 Handler 的首轮安全空表与二次自动生成流程可用。
- 保持 Manifest、Opcode Registry、Handler Registry 的构建前一致性校验。
- 若压测表明字典查询、运行时 Type 反序列化或类型转换成为瓶颈，再评估更细粒度的生成式 Parser/派发绑定。
- 每次调整生成器时验证 IL2CPP/AOT、HotUpdate DLL 与 YooAsset 资源同步。

### 验收标准

- 每包处理路径不出现 `MethodInfo.Invoke`、`DynamicInvoke`、运行时 Handler 扫描或运行时表达式编译。
- 生成内容可重复、可审查，删除 Handler 后不会阻断脚本编译。
- 构建前校验对 Proto、Manifest 和生成注册表给出明确失败信息。

## 阶段 7：Global 生命周期诊断

### 实施项

- 在 Development/Editor 模式记录 owner 获取次数、首次获取栈和持有时长。
- 场景切换或退出时输出未释放 owner 与仍 Pin 的组件清单。
- 为 `Pin` 和 `ForceRemove` 记录调用原因，禁止业务层用 `ForceRemove` 替代常规 `Remove`。
- 定期审查常驻组件：只有确实跨调用者、跨场景持续运行的服务才应 Pin。

### 验收标准

- 能定位“谁持有组件、持有几次、为何未释放”。
- 不在 Release 构建的热路径保留栈追踪或额外 GC。

## 阶段 8：UI、资源与对象池异步治理

### 实施项

- 窗口打开、预加载、资源加载和对象池创建统一使用 MTask Owner 任务域；不在业务方法签名中增加或转发取消令牌。窗口/场景关闭时通过 Owner 释放自动取消，阻塞 I/O 在 `OnDisposing()` 同步解除。
- 同资源路径的并发请求做 in-flight 去重，并以 `.Share()` 明确表达多方等待同一底层加载。
- 给 UI 缓存和对象池设置容量、淘汰和场景卸载策略。
- 异步完成时仍检查 owner、窗口或场景是否有效，避免外部回调写入已销毁对象；不以应用快速退出作为完成回调的可靠时机。

### 验收标准

- 窗口关闭或场景切换后不会出现延迟回调创建孤儿对象。
- 高速打开/关闭窗口时资源加载次数和对象池数量受控。

## 推荐执行顺序

| 顺序 | 阶段 | 原因 |
| --- | --- | --- |
| 1 | 阶段 0 | 没有数据就无法判断优化是否有效。 |
| 2 | 阶段 1 | 控制积压是网络稳定性的基础。 |
| 3 | 阶段 2、3 | 处理高并发时的生命周期、内存和超时压力。 |
| 4 | 阶段 4、5 | 根据实际业务决定协议升级和公网韧性投入。 |
| 5 | 阶段 6 | 持续验证已完成的生成式绑定，不在无数据时继续过度优化。 |
| 6 | 阶段 7、8 | 持续提升可维护性和异步资源正确性。 |
